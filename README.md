# TFG_GemmaBeatrizVate

### Encrypted IoT network traffic classification with JA4+ fingerprints

This thesis focuses on identifying and classifying network traffic using digital fingerprints based on the JA4+ algorithms. The main goal is to develop and evaluate an efficient method for analysing traffic patterns in network environments, making it possible to distinguish between different IoT devices and traffic behaviours even when communications are encrypted.

The project follows a complete pipeline:

1. Extract JA4+ fingerprints from a PCAP file using Zeek and the FoxIO JA4+ scripts.
2. Consolidate the Zeek logs into a single connection-level dataset.
3. Calculate `JA4X` from X.509 certificate information, because Zeek does not directly save the final JA4X fingerprint in the logs used here.
4. Extract raw/decomposed features from full JA4+ fingerprints.
5. Analyse fingerprint similarity between devices.
6. Train and evaluate different classification models using full fingerprints and decomposed fingerprint features.

The most important comparison in the work is between:

- **Full-fingerprint models**, where the complete fingerprint string or bundle is used as the input representation.
- **Decomposed-feature models**, where each fingerprint is split into individual components before classification.

## Project Workflow

## STEP 1: Extracting logs and fingerprints with Zeek

The FoxIO JA4+ repository is used to generate the fingerprints. In this phase, `Zeek` is used because it is faster and more suitable than a pure Python implementation for processing PCAP files and generating connection logs.

The only fingerprint not directly saved as a final value in the Zeek logs used by this project is `JA4X`. For that reason, `JA4X` is calculated later in Python from the certificate information available in `x509.log`.

Example execution:

```bash
cd /mnt/d/TFG_GemmaBeatrizVate
mkdir -p /mnt/d/TFG_GemmaBeatrizVate/1_Data/zeek_logs/logs
zeek -r 1_Data/Original_Pcaps/BenignTraffic.pcap \
  0_Init/ja4/zeek/__load__.zeek \
  Log::default_logdir=/mnt/d/TFG_GemmaBeatrizVate/1_Data/zeek_logs/logs
```

Files generated or used by Zeek:

| Fingerprint | Zeek log |
|---|---|
| `JA4` | `ssl.log` |
| `JA4S` | `ssl.log` |
| `JA4X` | calculated later from `x509.log` |
| `JA4H` | `http.log` |
| `JA4L` | `conn.log` |
| `JA4LS` | `conn.log` |
| `JA4T` | `conn.log` |
| `JA4TS` | `conn.log` |

For alternative scenarios or traffic captures, the same process can be repeated by changing the input PCAP and the output log directory.

## STEP 2: Consolidating fingerprints into a single CSV and creating JA4X

The main script for this phase is:

```bash
python3 2_Development/2_1_Preprocessing/combine_zeek_fingerprints.py
```

This script combines the logs generated by Zeek into a single connection-level dataset containing JA4+ fingerprints and associated IoT device information.

The `JA4X` extraction was implemented using the FoxIO Python `ja4x.py` script as a reference, adapting its logic to calculate the fingerprint from certificate information available in Zeek's `x509.log`: [FoxIO JA4X Python script](https://github.com/FoxIO-LLC/ja4/blob/main/python/ja4x.py).

### Files and modules used

- `2_Development/2_1_Preprocessing/combine_zeek_fingerprints.py`: main entry point. It orchestrates the complete combination process.
- `2_Development/2_1_Preprocessing/combine_zeek_fingerprints/config.py`: defines input and output paths, the source PCAP, the Zeek log directory, and the `MAC_TO_DEVICE` and `MAC_TO_CATEGORY` dictionaries.
- `2_Development/2_1_Preprocessing/combine_zeek_fingerprints/reader.py`: reads Zeek logs and extracts the `IP -> MAC` map from the PCAP using `tshark`.
- `2_Development/2_1_Preprocessing/combine_zeek_fingerprints/processor.py`: normalizes `conn.log`, `http.log`, and `ssl.log`, assigns devices, calculates/assigns `JA4X`, and joins the information by `connection_id`.
- `2_Development/2_1_Preprocessing/combine_zeek_fingerprints/ja4x.py`: calculates the `JA4X` fingerprint from the certificates in `x509.log`.
- `2_Development/2_1_Preprocessing/combine_zeek_fingerprints/__init__.py`: marks the folder as a Python package.

### Main inputs

- `1_Data/Original_Pcaps/BenignTraffic.pcap`
- `1_Data/zeek_logs/logs/conn.log`
- `1_Data/zeek_logs/logs/http.log`
- `1_Data/zeek_logs/logs/ssl.log`
- `1_Data/zeek_logs/logs/x509.log`

### Summary of the process

1. Extracts the real MAC addresses from the PCAP.
2. Reads the Zeek logs.
3. Normalizes the main connection, HTTP, and TLS columns.
4. Calculates `JA4X` from `x509.log`.
5. Links `JA4X` to TLS connections using certificate fingerprints available in `ssl.log`.
6. Assigns the device name and category from the MAC address.
7. Generates a final CSV by combining the connections from `conn.log` with the available information from `http.log` and `ssl.log`.

### Output

- `1_Data/zeek_logs/combined_fingerprints.csv`


## STEP 3: Extracting raw features from fingerprints

The main script for this phase is:

```bash
python3 2_Development/2_1_Preprocessing/extract_raw_features.py
```

This script takes the combined CSV generated in the previous step and splits the JA4+ fingerprints into simpler columns for later analysis or model training.

The fingerprint parameters extracted in this step are based on the JA4+ format described by FoxIO in [JA4+ Network Fingerprinting](https://blog.foxio.io/ja4+-network-fingerprinting), with the TCP fingerprint parameters based on [JA4T: TCP Fingerprinting](https://foxio.io/blog/ja4t-tcp-fingerprinting).

### Files and modules used

- `2_Development/2_1_Preprocessing/extract_raw_features.py`: main entry point for raw-feature extraction.
- `2_Development/2_1_Preprocessing/extract_raw_features/config.py`: defines the input file, output file, base columns, and expected fingerprint columns.
- `2_Development/2_1_Preprocessing/extract_raw_features/processor.py`: loads the CSV, calculates fingerprint coverage, converts timestamps, applies the active parsers, creates individual files, and saves the results.
- `2_Development/2_1_Preprocessing/extract_raw_features/parsers.py`: contains the functions that split each fingerprint into its components.
- `2_Development/2_1_Preprocessing/extract_raw_features/__init__.py`: exposes the package functions so they can be imported by the main script.

### Main input

- `1_Data/zeek_logs/combined_fingerprints.csv`

### Summary of the process

1. Reads the combined CSV.
2. Checks which fingerprint columns are available.
3. Converts Zeek timestamps into a readable format.
4. Extracts components from the fingerprints currently configured in `processor.py`: `JA4`, `JA4S`, `JA4X`, `JA4T`, `JA4TS`, and `SNI`.
5. Builds the final dataset with identification columns, original fingerprints, and extracted features.
6. Saves individual files by fingerprint type when applicable.

Important note: `parsers.py` also contains parsers for `JA4H`, `JA4L`, and `JA4LS`, but these parsers are commented out in the current active `processor.py`. Therefore, the current execution does not include decomposed `JA4H`, `JA4L`, or `JA4LS` feature columns in `raw_features.csv`.

### Outputs

- `1_Data/raw_fingerprints/raw_features.csv`
- `1_Data/raw_fingerprints/raw_features_excel.xlsx`
- Individual files in `1_Data/raw_fingerprints/individual_raw_fingerprints/`, for example:
  - `JA4_raw.csv`
  - `JA4S_raw.csv`
  - `JA4X_raw.csv`
  - `JA4T_raw.csv`
  - `JA4TS_raw.csv`
  - `SNI_raw.csv`

### Extracted feature summary

| Fingerprint | Number of extracted features | Example fields |
|---|:---:|---|
| `JA4` | 8 | TLS version, SNI type, cipher count, extension count, ALPN, hashes |
| `JA4S` | 6 | TLS version, extension count, ALPN, selected cipher, extension hash |
| `JA4X` | 3 | issuer hash, subject hash, extension hash |
| `JA4T` | 8 | TCP window size, option list, MSS, scale, TCP option flags |
| `JA4TS` | 8 | server-side TCP fields |
| `SNI` | 1 | server name |

## STEP 5: Model Evaluation

The modelling phase compares different ways of using JA4+ information to classify IoT network traffic.

### Model groups

- `dictionary_full_fingerprints`: dictionary-based classifiers using complete JA4+ fingerprint combinations.
- `rf_full_fingerprints`: Random Forest models using complete fingerprint strings or bundles.
- `rf_features`: Random Forest models using parsed fingerprint components as features.

### 5.1 Dictionary full-fingerprint models

This model group is located in:

- `2_Development/2_3_Models/dictionary_full_fingerprints/`

These notebooks evaluate device classification using complete fingerprint strings, without decomposing them into individual features. Each notebook tests a different fingerprint combination:

- `dictionary_ja4_full_fingerprint.ipynb`: uses only the conventional `JA4` client fingerprint.
- `dictionary_ja4+ja4x_full_fingerprint.ipynb`: uses `JA4` together with certificate fingerprint `JA4X`.
- `dictionary_ja4+ja4s_full_fingerprint.ipynb`: uses client and server TLS fingerprints.
- `dictionary_ja4+ja4s+ja4ts_full_fingerprint.ipynb`: adds the server TCP fingerprint `JA4TS`.
- `dictionary_ja4+ja4s+ja4t+ja4ts_full_fingerprint.ipynb`: adds both client and server TCP fingerprints.
- `dictionary_ja4+_full_fingerprint.ipynb`: uses the available full JA4+ combination.

Evaluation summary:

- Each row is represented as a full fingerprint bundle.
- Devices with too few samples are removed.
- Samples are split into training, validation, and test subsets.
- A dictionary is built from the training split, linking known fingerprint bundles to the device where they appeared.
- Validation data is used to select the best matching strategy.
- Test data is evaluated with accuracy, macro precision, macro recall, macro F1, top-k accuracy, prediction time, and dictionary usage rates.
- Predictions prioritize exact fingerprint matches, then partial fingerprint matches, and finally fallback rules.

### 5.2 Random Forest full-fingerprint models

This model group is located in:

- `2_Development/2_3_Models/rf_full_fingerprints/`

These notebooks evaluate the same full-fingerprint combinations as the dictionary models, but using a supervised Random Forest classifier. The complete fingerprint bundle is treated as a categorical input instead of being split into individual fields.

Notebook variants:

- `rf_ja4_full_fingerprint.ipynb`
- `rf_ja4+ja4x_full_fingerprint.ipynb`
- `rf_ja4+ja4s_full_fingerprint.ipynb`
- `rf_ja4+ja4s+ja4ts_full_fingerprint.ipynb`
- `rf_ja4+ja4s+ja4t+ja4ts_full_fingerprint.ipynb`
- `rf_ja4+_full_fingerprint.ipynb`

Evaluation summary:

- Each selected fingerprint combination is joined into a `signature_bundle`.
- Devices with too few samples are filtered out and large classes can be capped when needed.
- The full bundle is encoded as a categorical feature.
- All notebooks in this folder use the same split strategy: each device is split with `test_size=0.2`, so 80% of the samples are used for training and 20% are held out for final testing.
- Random Forest hyperparameters are selected with `GridSearchCV(cv=5)` on the training split. This creates internal validation folds inside the training data.
- The final model is evaluated on the test set.
- Test results include accuracy, macro precision, macro recall, macro F1, top-k accuracy, prediction time, and confusion matrices.

### 5.3 Random Forest decomposed-feature models

This model group is located in:

- `2_Development/2_3_Models/rf_features/`

These notebooks use the parsed fields generated during decomposed feature extraction. Instead of giving the model the full fingerprint string, each JA4+ component is represented as an individual feature. This makes it possible to inspect feature importance and evaluate whether a smaller subset of original fingerprint fields is enough for classification.

Notebook variants:

- `rf_ja4_decomposed.ipynb`: uses parsed `JA4` fields.
- `rf_ja4+sni_decomposed.ipynb`: uses parsed `JA4` fields together with SNI information.
- `rf_ja4+ja4x_decomposed.ipynb`: combines parsed `JA4` and `JA4X` fields.
- `rf_ja4+ja4s_decomposed.ipynb`: combines parsed `JA4` and `JA4S` fields.
- `rf_ja4+ja4s+ja4ts_decomposed.ipynb`: adds parsed `JA4TS` fields.
- `rf_ja4+ja4s+ja4t+ja4ts_decomposed.ipynb`: uses parsed client/server TLS and TCP fields.
- `rf_ja4+_decomposed.ipynb`: uses the available parsed JA4+ feature set.

Evaluation summary:

- The notebook loads `raw_features.csv` and keeps only the fields required for the selected experiment.
- Rows with missing required fingerprint components are removed.
- Devices are filtered by a minimum sample threshold, and large classes can be capped to reduce imbalance.
- Categorical parsed fields are encoded for Random Forest training.
- Numeric parsed fields are converted to numeric values.
- Random Forest configurations are evaluated with `GridSearchCV`.
- Macro F1 is used as the main selection criterion because the dataset has a strong class imbalance, so accuracy alone would favour majority classes.
- Feature importance is calculated from the trained model.
- The trained model and experiment metadata are saved when configured in the notebook.
- Final test evaluation reports accuracy, macro precision, macro recall, macro F1, top-k accuracy, prediction time, and confusion matrices.
- A top-feature retraining step rebuilds the model using only the most relevant original parsed fields and compares it with the full-feature model.
